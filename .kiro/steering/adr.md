# Architectural Decision Records (ADR)

This directory contains Architectural Decision Records for the SRE Copilot HITL project.

## Purpose

Architectural Decision Records document the key architectural decisions made during the development of the SRE Copilot system. Each ADR captures:
- The context and problem being solved
- The decision made
- The consequences (positive and negative)
- Any alternatives considered

## Current ADRs

### ADR-001: Architectural Safety Invariant

**Status**: Approved

**Context**: The SRE Copilot is a critical infrastructure system where AI/LLM components propose remediations, but infrastructure modifications must be approved by humans. We needed to ensure there is no possibility of AI components executing state-changing operations directly.

**Decision**: We established a strict architectural safety invariant that separates concerns into six distinct roles:
- **AI recommends**: The AI Diagnosis Engine analyzes evidence and proposes root causes and remediation actions
- **Policy evaluates**: The Policy/Risk Engine evaluates operational impact and calculates risk scores
- **Human authorizes**: The HITL Approval component provides explicit human authorization for state-changing operations
- **Automation executes**: The Execution Engine executes only pre-authorized actions
- **System verifies**: The Verification Engine checks if remediation achieved desired outcomes
- **Audit records**: The Audit System records all decisions, recommendations, and actions

**Consequences**:
- Positive: Clear separation of concerns makes the system auditable and prevents unauthorized state changes
- Positive: Each component can be tested and verified independently
- Negative: More complex architecture with multiple components and coordination points

**References**: Requirements 1, 5, 6, 10; Design Overview, Security Architecture Diagram

### ADR-002: HITL Approval Pattern

**Status**: Approved

**Context**: All state-changing operations in the SRE Copilot must require explicit human approval, regardless of risk level. This is a non-negotiable security requirement.

**Decision**: We implement a Task Token Callback Pattern using AWS Step Functions:
- Step Functions invokes HITL Approval Lambda with a Task Token generated by the service
- The workflow enters a waiting state (NOT an error state) - it remains paused but active
- The approval Lambda extracts and securely stores the Task Token (never logs it)
- An approval request is sent to the designated channel (email/Slack/Teams) WITHOUT the token
- The approver responds with APPROVE or REJECT via a secure callback URL
- The Approval Callback Service validates the request, retrieves the associated Task Token
- Based on the decision, the callback service calls `SendTaskSuccess` (APPROVE) or `SendTaskFailure` (REJECT)
- Step Functions resumes and branches according to the approval decision
- Timeout-based auto-rejection after configurable period (default 300 seconds)

The workflow MUST support three distinct outcomes:
- **APPROVE**: Continue to SSM remediation execution
- **REJECT**: Update status to REMEDIATION_REJECTED, NO SSM execution occurs
- **TIMEOUT**: Update status to TIMEOUT_EXCEEDED, NO SSM execution occurs

**Consequences**:
- Positive: Zero possibility of unauthorized state changes
- Positive: Configurable timeout allows flexibility for different environments
- Negative: Requires state machine orchestration rather than simple Lambda chains
- Negative: Additional complexity in handling approval tokens securely

**References**: Requirements 5, 6; Design, Component Interaction Diagram

### ADR-003: Component Separation

**Status**: Approved

**Context**: The SRE Copilot must clearly separate AI diagnosis from execution to enforce security boundaries and enable independent testing.

**Decision**: Each major function is implemented as a separate AWS Lambda function with specific IAM roles:
- Alert Ingestion Lambda: Receives and validates events
- Incident Manager Lambda: Creates and maintains incident records
- Diagnosis Engine Lambda: Calls Bedrock for log analysis
- Risk Assessment Lambda: Evaluates remediation risk and identifies SSM Runbooks
- SSM Executor Lambda: Executes approved runbooks
- Verification Engine Lambda: Performs health checks after remediation
- Audit Logger Lambda: Records all events to S3

**Consequences**:
- Positive: Each component has minimal permissions (least privilege)
- Positive: Components can be developed, tested, and deployed independently
- Positive: Debugging is easier as issues are isolated to specific components
- Negative: More complex deployment with multiple Lambda functions

**References**: Design, Component Interaction Diagram

### ADR-004: Task Token Callback Pattern

**Status**: Approved

**Context**: Step Functions workflows need to wait for external human approval before proceeding, but cannot block indefinitely.

**Decision**: We use Step Functions Task Tokens for asynchronous callback:
- The approval task includes a Task Token generated by Step Functions in its input
- The workflow enters a waiting state (NOT a failure state)
- The Task Token is extracted and stored securely by the Approval Lambda
- The approval handler sends a callback URL to the approver (without the token exposed)
- When the approver responds, the callback service validates the request and retrieves the token
- The callback service sends the token back with `SendTaskSuccess` or `SendTaskFailure`
- Step Functions resumes based on the callback result

This pattern is used for HITL approval waiting. SSM execution status may be handled independently using the execution mechanism defined by the approved design.

**Consequences**:
- Positive: Efficient use of AWS resources (no long-running state machine instances)
- Positive: Clear separation between workflow orchestration and task execution
- Negative: Requires careful token management to avoid token leaks or misuse

**References**: Design, Workflow Diagram

### ADR-005: Audit Trail Storage

**Status**: Approved

**Context**: All decisions, recommendations, approvals, and executions must be recorded for compliance and post-incident analysis.

**Decision**: We use S3 as the audit storage backend with the following characteristics:
- Immutable storage using S3 Object Lock (WORM - Write Once Read Many), configurable via IaC (disabled for MVP, enabled for production)
- Configurable retention period (default 30 days)
- Server-side encryption with KMS keys
- Structured JSON events with consistent schema (timestamp, actor, action, details)

**Consequences**:
- Positive: Audit trail cannot be tampered with or deleted
- Positive: Configurable retention allows compliance with different regulatory requirements
- Negative: S3 API calls add latency to each operation
- Negative: Requires additional IAM permissions for S3 access

**References**: Requirements 1, 2, 6, 7; Design Security Architecture Diagram

### ADR-006: IAM Authentication for Bedrock

**Status**: Approved

**Context**: The Diagnosis Engine needs access to AWS Bedrock for LLM analysis, but we want to avoid managing secrets for service authentication.

**Decision**: We use IAM role-based authentication for Bedrock access instead of API keys or Secrets Manager:
- Lambda execution roles are granted `bedrock:InvokeModel` permission
- No API keys or credentials are stored in code or Secrets Manager
- Temporary credentials are automatically rotated by AWS

**Consequences**:
- Positive: No secrets management overhead
- Positive: Automatic credential rotation by AWS
- Positive: Fine-grained permission control via IAM policies
- Negative: Less flexibility for cross-account access patterns

**References**: Design Security Architecture Diagram

### ADR-007: MVP Scope

**Status**: Approved

**Context**: We need to deliver a minimal viable product to validate the core workflow before adding complexity.

**Decision**: The MVP includes:
- Single complete scenario: Critical service failure on EC2/SSM-managed node
- One remediation type: Service restart via SSM Runbook (not instance restart)
- One environment: Development/staging
- Basic audit trail: 30-day retention
- Single approval channel: Email/Slack/Teams (configurable)
- S3 Object Lock disabled for MVP, enabled for production

**Consequences**:
- Positive: Faster time to first deployment
- Positive: Easier testing and debugging with simpler code paths
- Negative: Limited to one scenario; additional scenarios require new development
- Negative: Environment-specific configurations not yet separated

**References**: Design MVP Scope section

### ADR-008: Incident Lifecycle States

**Status**: Approved

**Context**: Incidents need clear state transitions to track their progress and enable proper workflow orchestration.

**Decision**: We define the following incident lifecycle states:
- `CREATED`: Incident record created, evidence collection pending
- `EVIDENCE_COLLECTED`: Evidence gathered, diagnosis pending
- `DIAGNOSIS_COMPLETE`: Diagnosis generated, risk assessment pending
- `RISK_ASSESSED`: Risk assessed, HITL approval pending
- `APPROVED`: Approved for remediation, execution pending
- `EXECUTING`: SSM Runbook execution in progress
- `RECOVERY_VERIFIED`: Health check passed, incident resolved
- `RECOVERY_FAILED`: Health check failed, incident not resolved
- `VERIFICATION_ERROR`: Health check could not be performed
- `REMEDIATION_REJECTED`: Remediation rejected by human approver
- `TIMEOUT_EXCEEDED`: Approval timeout exceeded, no execution
- `DIAGNOSIS_FAILED`: Bedrock analysis failed
- `DIAGNOSIS_TIMEOUT`: Bedrock analysis timed out

**Key State Transitions**:
- APPROVE ? Execute SSM Runbook
- REJECT ? REMEDIATION_REJECTED (no execution)
- TIMEOUT ? TIMEOUT_EXCEEDED (no execution)
- SSM SUCCESS + Health Verify SUCCESS ? RESOLVED
- SSM SUCCESS + Health Verify FAIL ? RECOVERY_FAILED

**Critical**: Execution success does NOT equal recovery verified. Only Health Verification SUCCESS leads to RESOLVED.

**Consequences**:
- Positive: Clear visibility into incident status
- Positive: State machine transitions can be validated
- Negative: More complex state management logic

**References**: Requirements 1, 2, 3, 4, 7, 8

## ADR Process

### Creating a New ADR

1. Create a new file named `adr-####.md` (where #### is a sequential number)
2. Use the following template:

```markdown
# ADR-####: [Title]

**Status**: [Proposed | Approved | Implemented | Deprecated | Superseded]

**Context**: [Description of the problem and context]

**Decision**: [The decision we made]

**Consequences**: [Positive and negative consequences]

**References**: [Links to related requirements, design documents, or other ADRs]
```

3. Add the new ADR to the list above in reverse chronological order
4. Submit the ADR for review along with the associated design changes

### ADR Lifecycle

- **Proposed**: New ADR under review
- **Approved**: ADR accepted, implementation can begin
- **Implemented**: ADR has been implemented in code
- **Deprecated**: ADR is no longer valid (should be superseded)
- **Superseded**: ADR has been replaced by a newer ADR
