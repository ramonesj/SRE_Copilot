## AWS Documentation Information Retrieved

### 1. Task Token Pattern

**Source**: AWS Step Functions Documentation

**Key Information**:

- Task tokens are generated by Step Functions when tasks are assigned to a worker
- Task tokens are available in the context object when a workflow enters a task state
- Task tokens can be passed to certain AWS SDK service integrations
- The task remains on hold until it receives the task token back through a SendTaskSuccess or SendTaskFailure call

### 2. SendTaskSuccess API

**Source**: AWS Step Functions API Reference

**Request Parameters**:
- `output`: JSON output of the task (max 262144 bytes)
- `taskToken`: The token that represents this task (min 1 char, max 2048 chars)

**Response**: HTTP 200 with empty body on success

**Error Codes**:
- `InvalidOutput`: The provided JSON output data is not valid
- `InvalidToken`: The provided token is not valid
- `TaskDoesNotExist`: The activity does not exist
- `TaskTimedOut`: The task token has expired or the task has already been closed
- `KmsAccessDeniedException`, `KmsInvalidStateException`, `KmsThrottlingException`

### 3. SendTaskFailure API

**Source**: AWS Step Functions API Reference

**Request Parameters**:
- `taskToken`: The token that represents this task (required)
- `error`: The error code of the failure (optional, max 256 chars)
- `cause`: A more detailed explanation of the cause of the failure (optional, max 32768 chars)

**Response**: HTTP 200 with empty body on success

**Error Codes**:
- `InvalidToken`: The provided token is not valid
- `TaskDoesNotExist`: The activity does not exist
- `TaskTimedOut`: The task token has expired or the task has already been closed
- `KmsAccessDeniedException`, `KmsInvalidStateException`, `KmsThrottlingException`

### 4. Callback Timeout Behavior

**Source**: AWS Step Functions Blog Post

**Key Information**:

- Unless a timeout is specified in the state machine definition (up to one year), the activity task state waits indefinitely
- The task pauses until the activity worker calls either SendTaskSuccess or SendTaskFailure
- Timeout can be configured up to one year for Standard workflows

### 5. IAM Permissions

**Required Permissions for Callback Completion**:

- `states:SendTaskSuccess`: Permission to report task completion successfully
- `states:SendTaskFailure`: Permission to report task failure

These permissions must be granted to the Lambda function or service that will call the callback APIs.

## How Information Was Applied to SRE Copilot

### Architecture Assessment

The AWS Documentation MCP research confirmed the following aspects of the SRE Copilot HITL architecture:

#### 1. Task Token Usage

**Status**: ✅ CONSISTENT

**Verification**:
- SRE Copilot correctly uses Step Functions Task Tokens for callback pattern
- Token is passed to external approval system via Step Functions workflow
- External system returns token with approval decision via SendTaskSuccess or SendTaskFailure

#### 2. APPROVE Path

**Status**: ✅ CONSISTENT

**Verification**:
- SRE Copilot design specifies APPROVE response triggers SendTaskSuccess
- SendTaskSuccess resume workflow to next state (SSM execution)
- AWS documentation confirms this is the expected callback pattern

#### 3. REJECT Path

**Status**: ✅ CONSISTENT

**Verification**:
- SRE Copilot design specifies REJECT as a valid business/workflow outcome
- REJECT decision is returned through the controlled callback path
- Step Functions resumes and Choice evaluates the decision
- REJECT routes to "HandleRejection" state, updating status to REMEDIATION_REJECTED
- SSM executor Lambda is NOT invoked for REJECT decisions
- The critical invariant REJECT => NO SSM is maintained

#### 4. TIMEOUT Path

**Status**: ✅ CONSISTENT

**Verification**:
- SRE Copilot design specifies timeout triggers States.Timeout error
- Catch block handles States.Timeout with appropriate state transition
- AWS documentation confirms timeout behavior (up to one year for Standard workflows)

#### 5. SSM Execution Prevention

**Status**: ✅ CONSISTENT

**Verification**:
- SRE Copilot architecture ensures SSM execution only after explicit APPROVE
- REJECT and TIMEOUT paths never reach SSM executor Lambda
- Task Token callback pattern ensures human authorization boundary is respected

#### 6. Task Token Security

**Status**: ✅ CONSISTENT

**Verification**:
- SRE Copilot stores Task Tokens using the protected persistence mechanism defined in the security design
- Task Tokens are sensitive callback credentials and must be:
  - never appear in application logs
  - never appear in user-facing interfaces
  - never be included in EventBridge events
  - accessible only by the authorized callback component
  - associated securely with the correct approval request and workflow execution
  - remain protected at rest if persisted
- AWS documentation confirms token is sensitive authentication material
